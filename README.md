## 3. Відповіді на теоретичні питання

## Частина 1 - Завантаження даних та проєктування схеми

### 1. Чому аудіо-характеристики винесені в окремий об’єкт audio_features, а не зберігаються плоско? Коли таке вкладення вигідне, а коли створює проблеми?

Необхідність в групуванні плоскої структури у вкладену має наступні переваги:
- Легкість читання структури, оскільки всі поля audio_features вкладені в один об'єкт;
- Легкість включення повного об'єкту в результат.

Та недоліки:
- Ускладнення написання запиту при необхідності прописання повного шляху до одного поля.

### 2. Чому виконавці зберігаються як масив, а не як рядок? Які запити стають простішими?

Бо рядок сприймається як один виконавець, та масив дозволяє зберігати кілька виконавців.
Та якщо зберігання як масиву дозволяє нам легко групувати виконавців та відокремлювати їх
один від одного за допомогою unwind, а не розділяти за крапкою з комою кожного разу.

### 3. Що таке $out і чим він відрізняється від $merge? Коли використовувати кожен?

Обидва використовуються в aggregation pipeline для запису результатів в окрему колекцію.

Та відмінність:
- $out завжди очищує колекцію перед записом;
- $merge дозволяє дозаписувати документи в колекцію, не очищуюючи її.

## Частина 2 - Запити до даних

### 1. Для чого використовується інструкція $unwind?

Для розбиття масиву на окремі документи. Тобто якщо у масиві було 3 виконавці,
то після unwind буде 3 окремих документів, де кожен документ буде містити одного виконавця.

### 2. Чим $stdDevPop відрізняється від $stdDevSamp?

Обидва використовуються для обчислення стандартного відхилення.

Та відмінність:
- $stdDevPop - стандартне відхилення генеральної сукупності;
- $stdDevSamp - стандартне відхилення вибірки.

## Частина 3 - Аналітика через Aggregation Pipeline

### 1. У запиті 1 ми фільтруємо виконавців, у яких менше 5 треків. Як зміниться результат, якщо знизити поріг до 1? А що станеться, якщо вибирати виконавців із більш ніж 50 треками? Поясніть результат.

Якщо зменшувати фільтр по трекам, то avgPopularity збільшується, бо в топ потрапляють артисти, в яких
є лише один трек, та це якось стало хітом.
Та при збільшенні фільтру - avgPopularity зменшується, та це вже продуктивні артисти з хочаб 50 треками
в яких є лояльні фанати.

### 2. У запиті 3 ми фільтруємо жанри з менше ніж 100 треками. Чи зміниться результат, якщо знизити поріг до 50? Поясніть результат.

Поправка: на поточній базі на кожен жанр існує рівно 1000 треків, тому фільтрування менше ніж 1000
завжди поверне 0 результатів.

Але якщо мати фільтр "більше ніж", то результатом буде всі possible результати, допоки фільтр не перевищить
планку у 1000. Та якщо перевищить - то результат буде порожнім.

### Завдання 3. Покривний запит

Припустимо, що індекс із завдання 1 вже існує.

Дано запит:

```javascript
db.tracks.find({
  track_genre: "pop",
  popularity: { $gte: 70 }
});
```

#### Питання: Чи є цей запит покривним (covered query)? Надайте розгорнуту та обґрунтовану відповідь у файлі README.

Ні, це не є покривним запитом, бо навіть якщо фільтрація існує який має всі або менше ключів індексу,
в кінці має ще бути проекція щоб включити тільки ті поля які входять в індекс. Інакше MongoDB буде змушена
додатково читати з диску недостаючі поля поза індексом.
